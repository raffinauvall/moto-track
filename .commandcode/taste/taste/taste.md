# Taste
- Communicates in casual, informal Indonesian (Jakarta slang: "lu", "gua", "deh", "sekalian") and expects the assistant to respond in the same casual register. Confidence: 0.9
- Delegates execution with minimal instructions — e.g. a single "lanjut" to approve continuing a plan — and expects the assistant to carry out the rest of the agreed work (refactors, cleanup, verification) autonomously without step-by-step check-ins. Confidence: 0.6
- Reports problems in terse one-liners with minimal context (e.g. "ada error login failed to fetch", "ada error tuh" — sometimes with no detail at all, or just pasted logs ending with "nih") and expects the assistant to investigate the root cause autonomously — probing the actual environment (endpoint reachability, DNS, config, typecheck/build) — and explain the cause with actionable next steps rather than asking clarifying questions first. Confidence: 0.85
- Treats web (expo web) as a casual, secondary test target ("gua iseng test di web doang") while native (Android/iOS) is the primary platform — so native-only modules that crash the web bundle (e.g. `react-native-maps`) must be handled per-platform with a `.web.tsx` placeholder, and native features must NOT be removed just to accommodate web. Confidence: 0.6
- Wants the codebase architecture kept tidy and well-organized, following conventional React/TypeScript layering: data access goes through a dedicated API layer (never direct DB/Supabase calls from screens or components), reusable logic lives in hooks, and global state lives in context. Confidence: 0.8
- Prefers naming conventions that are consistent and self-consistent: API functions in camelCase (`getMotor`, `addMotor` — not PascalCase `GetMotor`), hook file names matching the hook they export (`useServiceDetails.ts` for `useServiceDetails`, not `useDetailServiceHistory.ts`). Confidence: 0.6
- Prefers a barrel file (e.g. `src/api/index.ts`) that re-exports the whole API layer so consumers can import once from a single path instead of reaching into individual files. Confidence: 0.5
- Likes dead/unused files and duplicate implementations removed during refactors (empty hooks, unused API files, duplicated helpers), and verifies the refactor is behavior-preserving (typecheck + lint, comparing against a clean tree via git stash to confirm remaining errors are pre-existing). Confidence: 0.6
- Approves of work-in-progress verification steps that include checking the previous state (e.g. `git stash` + `git status`/`stash list` to confirm changes are safe) before declaring a refactor complete. Confidence: 0.5
- When debugging runtime connectivity/config issues (e.g. "failed to fetch" on login), wants the assistant to verify the root cause empirically from the environment — probing the endpoint with curl, checking DNS resolution, comparing against known-good hosts — before diagnosing, and to distinguish infrastructure/network causes from app-code causes. Confidence: 0.5
- Wants project documentation (README) as part of the deliverables, and expects it to be comprehensive and grounded in the actual codebase — features, tech stack table, project structure tree, setup/config steps, auth flow, and troubleshooting — rather than a generic template. Confidence: 0.4
- Runs and tests the project on a physical Android phone via Expo Go (not an emulator), so run/setup guidance should account for Expo Go's single-SDK-per-release constraint and the device's own limitations rather than assuming emulator workflows. Confidence: 0.5
- Wants an improvement plan written as a markdown document before any implementation starts ("bikin improvement plan dlu ya di pake markdown"), with phased phases, files touched, and verification steps — then executes against that plan. Confidence: 0.9
- When offered scope options for a plan, picks the comprehensive all-inclusive roadmap ("Semua ide sekaligus" — all ideas at once, phased) rather than the minimal recommended scope. Confidence: 0.5
- Pauses a session mid-plan to run/test the project themselves ("gua mau run project dlu... jadi gua berhentiin dulu") and expects a concise checkpoint summary of completed vs. remaining phases plus any run-blocking caveats (e.g. native module rebuild, schema changes), so work can resume later with a simple "lanjut". Confidence: 0.5
- Explicitly asks for UI beautification/polish alongside feature work ("perbaiki dan percantik UI nya") — values visually polished screens, not just functional correctness, and expects the assistant to fold new feature requests (e.g. map in ride history) into the existing phased plan rather than treating them as separate work. Confidence: 0.5
- Rejects features that add no value given the app's architecture — e.g. cancelled a data-export/backup feature with "gaperlu cuy, karena data kan simpan di db" — and expects the whole feature (code + now-unused dependencies) to be fully reverted/cleaned up. Confidence: 0.7
- For manual operations the user must perform outside the codebase (e.g., running SQL migrations in the Supabase dashboard SQL Editor), expects concrete click-by-click instructions — exact navigation path, button names, expected success output — with the full content inlined as fallback, plus an offer to debug whatever error they paste back. Confidence: 0.5
